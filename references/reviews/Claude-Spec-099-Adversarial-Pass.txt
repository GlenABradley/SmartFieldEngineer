
Adversarial Pass — Slice 1 Build Spec 0.99
Starting light, escalating to structural risk, then back down.
Light: naming/schema friction
"reservation" is overloaded across documents. The commercial brief talks about "protected reservations" in the context of inventory/parts. This spec's reservation.put is purely time/site (starts_at, ends_at, resources, components_minutes). If anyone on the team reads "reservation" and thinks "parts hold," they'll build the wrong thing. Rename or add a one-line disambiguation note before code generation — cheap now, expensive after two implementers diverge.
secured_on_hold gate is schema theater. It requires stabilization_text to literally begin with the string "SOURCED:". A technician can satisfy this with "SOURCED: asdf" — the validation is a string-prefix check, not evidence of sourcing. This gives false confidence that the interruption record means something. Either require an actual evidence_id (stronger) or stop implying the text convention proves anything — don't let a magic prefix masquerade as an integrity control.
Medium: unaddressed operational edges
WAL + backup consistency isn't specified. You mandate WAL mode and a backup step that bundles "consistent DB + every referenced blob," but never say how consistency is achieved while the writer holds the lock. WAL leaves -wal/-shm sidecar files. Does backup.create force a checkpoint first? Copy the sidecars? If not, a backup taken mid-session can restore to a state that's missing committed-but-uncheckpointed data. This is exactly the kind of gap the "never" language in §2 (no last-write-wins on commitments) is supposed to prevent — but it's silent on backup-time consistency, which is the same failure mode wearing a different hat.
Import idempotency is undefined. §9 says "do not upgrade the source in place" and "no pending-action replay," but never says what happens if --maintenance import is run twice against the same 0.2.0 source (partial failure, operator confusion, retry). Given the spec's obsessive idempotency elsewhere (operation_id fingerprints, two-phase evidence publish), leaving import re-run behavior unspecified is a visible inconsistency in an otherwise fail-closed document.
Windows path canonicalization is underspecified for the actual threat model. "Canonicalize paths so C:\Data\HomeA and a junction to it are one store" — but NTFS also has 8.3 short names, subst drive mappings, and case-insensitive-but-case-preserving semantics that can alias paths without detection. If the two-Home isolation guarantee (the whole point of §13's test) depends on path canonicalization catching aliasing, this needs GetFinalPathNameByHandle-level rigor stated explicitly, not just "junctions."
Encrypted-volume detection needs a stated mechanism. encrypted_volume: yes|no|unknown implies a BitLocker (or equivalent) status check, which on Windows can require elevated privileges the app otherwise doesn't need. If the install flow doesn't run elevated, this field silently degrades to unknown forever on a large fraction of real machines — worth stating now, not discovering during the Windows trial.
Heavy: architectural tension
The in-process transport option quietly breaks Law #1. Law 1 says "GUI, helper, and any future model cannot write the ledger" — a boundary the spec elsewhere treats as load-bearing (§7's Pre-answered Attacks table exists because of process/session isolation). But §4 permits collapsing to an "in-process single-writer queue" as a two-day spike, with the claim that "application methods and receipts stay identical." Identical receipts don't make it the same boundary — if GUI and core share a process, the command boundary is a coding convention, not an enforced barrier, and every guarantee in §11 (HOME_CONTEXT leak resistance, etc.) becomes trust-based rather than structurally true. If the in-process spike ships to real customers, that's a materially weaker product than what §17's "pre-answered attacks" table advertises. Recommendation: either forbid in-process for anything beyond dev/test, or explicitly downgrade the Law 1 claim when in-process mode is active so nobody mistakes the spike for the hardened build.
The biggest structural risk isn't a bug — it's scope calibration. Slice 1 is framed as "a laptop office that still works when the SIM is in a drawer" for one trusted operator, yet it specifies dual-Home isolation, cross-Home leak resistance (§17's whole attack table), session-generation fencing, and a mandatory two-Home adversarial test as first-class acceptance criteria (§13). That's multi-tenant security engineering bolted onto a single-user offline tool, and it's a large chunk of the 152–240 hour estimate. Ask directly: does the Slice 1 buyer (one owner, one laptop) need Home-isolation hardening on day one, or is this pulling a later-slice concern (the sponsor/shared-deployment tier from the commercial brief) forward into the critical path of the first shippable thing? If two Homes on one machine is just "context switching for a person who does side work," the isolation bar can be much lower than what §17 demands. If it's actually pre-hardening for the sponsor tier, say so explicitly and account for it in the estimate — right now it's presented as if it were free.
Back to light: what to preserve
The fail-closed default, the "Confirmed ≠ paid/booked/safe" vocabulary discipline, the two-phase evidence publish with fingerprint-based replay safety, and the refusal to let billing: settled_recorded proceed without a source reference are all genuinely strong and shouldn't be touched. The error-code table in §11 is unusually disciplined — keep it as the arbiter, don't let implementers invent new codes ad hoc.
Single sharpest question for the team
Before generating code: is the two-Home isolation test in §13 actually required for Slice 1's buyer, or is it silently importing the sponsor-tier threat model early? That one answer changes the hour estimate, the transport decision (in-process becomes much more defensible if there's truly one Home, one operator, one process), and possibly the whole shape of §7. Everything else here is a fixable detail; that one is a scope decision hiding inside what reads as a technical spec.
